# Database Proposal

## Scope

This document defines the SQLite model implemented in Part 6 for the Project Management MVP.

The MVP has:

- Multiple users supported by the schema, even though the current demo has one user.
- One Kanban board per user.
- Board state saved as one validated JSON document.
- Local SQLite storage inside the Docker environment.

## Storage Location

The database file should be stored at `/data/project-management.db` in the container. Docker Compose should mount a named volume at `/data` so rebuilding or stopping the container does not delete user data.

For local backend tests, the database path should be configurable and point to a temporary file. The application should create the parent directory and database file when they do not exist.

## Tables

### `users`

| Column | SQLite type | Constraints | Purpose |
| --- | --- | --- | --- |
| `id` | `TEXT` | `PRIMARY KEY` | Stable user identifier, generated by the application. |
| `username` | `TEXT` | `NOT NULL UNIQUE` | Login name. Comparison is case-sensitive unless the API normalizes it explicitly. |
| `password_hash` | `TEXT` | `NOT NULL` | Password hash for the future backend sign-in flow. Plaintext passwords are never stored. |
| `created_at` | `TEXT` | `NOT NULL` | UTC timestamp in ISO 8601 format. |
| `updated_at` | `TEXT` | `NOT NULL` | UTC timestamp in ISO 8601 format. |

The initial seed user represents the current demo account `user` / `password`. The password is inserted as a generated password hash, not as plaintext. Backend login issues an in-memory bearer token for the local MVP; the frontend stores that token in browser `localStorage`.

### `boards`

| Column | SQLite type | Constraints | Purpose |
| --- | --- | --- | --- |
| `id` | `TEXT` | `PRIMARY KEY` | Stable board identifier. |
| `user_id` | `TEXT` | `NOT NULL UNIQUE`, foreign key to `users(id)` with `ON DELETE CASCADE` | Board owner; `UNIQUE` enforces one board per user. |
| `name` | `TEXT` | `NOT NULL` | Board display name, initially `Kanban Studio`. |
| `board_json` | `TEXT` | `NOT NULL`, valid JSON object | Serialized board document. |
| `version` | `INTEGER` | `NOT NULL`, default `1`, positive | Optimistic-concurrency version for safe updates. |
| `created_at` | `TEXT` | `NOT NULL` | UTC timestamp in ISO 8601 format. |
| `updated_at` | `TEXT` | `NOT NULL` | UTC timestamp in ISO 8601 format. |

SQLite foreign-key enforcement must be enabled for every connection with `PRAGMA foreign_keys = ON`.

The board row should be updated in one transaction. Each successful update increments `version` and refreshes `updated_at`.

## Board JSON Contract

`board_json` follows the frontend `BoardData` shape:

```json
{
  "columns": [
    {
      "id": "col-backlog",
      "title": "Backlog",
      "cardIds": ["card-1"]
    }
  ],
  "cards": {
    "card-1": {
      "id": "card-1",
      "title": "Align roadmap themes",
      "details": "Draft quarterly themes with impact statements and metrics."
    }
  }
}
```

### Validation rules

- The root value must be a JSON object with exactly `columns` and `cards` at the API boundary. Extra fields should be rejected rather than silently discarded.
- `columns` must be a non-empty array.
- Every column must have a non-empty string `id`, a string `title`, and a `cardIds` array.
- Column IDs must be unique.
- `cards` must be an object keyed by card ID.
- Every card must have an `id`, `title`, and `details`, all strings; the card ID must equal the key.
- Card IDs must be unique and every card must appear in exactly one column's `cardIds` array.
- Every `cardIds` entry must refer to an existing card.
- No card may be omitted from the columns or listed more than once.
- Titles and details may be empty only where the existing UI permits them; new card titles must be non-empty after trimming.
- Column and card ordering is the order of the arrays, not database row order.

The SQLite `CHECK (json_valid(board_json))` constraint catches malformed JSON. Application validation must enforce the structural and ownership rules above because SQLite JSON validity alone is insufficient.

## Initialization and Seeding

On application startup or first database access:

1. Create the database parent directory if needed.
2. Create `users` and `boards` tables using the schema version supported by the application.
3. Enable foreign keys.
4. Insert the demo user if it does not exist.
5. Create that user's board from the existing `initialData` if it does not exist.

Initialization must be idempotent. Running it repeatedly must not reset an existing board or overwrite user changes.

A lightweight schema version table or migration mechanism should be added when the first schema change is needed. For the initial MVP, `CREATE TABLE IF NOT EXISTS` is sufficient if the implementation records the chosen schema version.

## API and Update Semantics

The authenticated user is the owner identity for all board reads and writes. The API must query by the authenticated user's ID, never by an arbitrary user ID supplied by the browser.

Board updates should use this sequence:

1. Authenticate the user.
2. Load the user's board and current `version`.
3. Validate the proposed board document.
4. Update `board_json`, `version = version + 1`, and `updated_at` in one transaction.
5. Return the saved canonical board and version.

If a client supplies an outdated version, the API returns a conflict instead of silently overwriting a newer board. The frontend sends the version it last loaded, serializes saves in a client-side queue, and displays save errors without discarding the local edit.

## Security and Privacy

- Do not store plaintext passwords.
- Do not expose `password_hash` through any API response.
- Do not accept a user ID as proof of ownership.
- Keep the SQLite file under the mounted data directory and out of source control.
- Keep OpenRouter credentials unrelated to board JSON and server-side only.

## Implementation Status

Part 6 implements this model and its backend board routes. Part 7 connects the frontend through a same-origin typed API client. The Docker Compose `app-data` named volume persists `/data/project-management.db` across container restarts.
